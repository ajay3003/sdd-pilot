# BirkNext unified scope — implementation report (Stage 1–2 foundation)

**Date:** 2026-11-13 · branch `008-traceability-first` · local commit only (no push, no deployment, no remote calls).

## Principle

There is one canonical system identity and one shared scope identity, and each module keeps its own domain responsibility.

- **Systems and connections** are not a new registry. They are the canonical interpretation entities (`CanonicalEntityType.System` / `Service`) and their relationships for the active Target Environment profile. The system identity is `CanonicalEntityView.Key`.
- **Scopes** are the one new store: a project-local Scope Registry (`scope_registry` schema). A scope holds typed *references* (system, relationship, scenario, requirement, journey, contract, test case, test data asset, …), never copies of the referenced data.
- Modules (E2E, Contract Testing, Impact Analysis, Delivery Reports, Test Plan Suggestions) stay owners of their own results. They would *read* a scope selection as a filter. Selecting a scope never authorizes execution.

## Implemented

| Area | What |
|---|---|
| Shared contracts | `AIAssisted/shared/ScopeRegistryContracts.cs` (`BirkNext.Scopes`), linked into the Api and Web projects |
| Store | `ScopeRegistryDbContext`, with tables `scope` and `scope_revision` (members as jsonb); additive migration `InitialScopeRegistry`; a schema check entry and startup migrate |
| Rules | `ScopeRegistryRules`: normalize (dedupe by `Kind:TargetId`, drop empty ids), fingerprint, compare revisions, multi-scope selection (union of Confirmed members with attribution and per-scope counts) |
| Lifecycle | Create as draft revision 1 (the name is unique per project). Edit a draft in place. An edit after approval creates a new draft revision, and the approved revision stays immutable. Approving the newest revision supersedes the previous approved one (kept readable). Archive. Every write passes a `Version` concurrency token, and a stale write gets 409 and is not merged |
| API | `api/scopes`, project-scoped by `projectKey` on every route. Approve and archive need the `SystemConfigurationWrite` policy, with the actor derived from the request, never supplied by the client |
| UI | `/project-scopes` "Systems & Scopes" with tabs Systems (canonical systems and the scopes they belong to), Connections (canonical outgoing/incoming relationships, labelled as interpretation and not verified runtime connections) and Scopes (editor with a system picker by canonical key, other members by id, save draft, approve with rationale, compare revisions, history) |
| Nav and docs | Workspace nav item (gated by Sample Projects or Source Analysis), documentation catalog entry, User Guide paragraph `guide-project-scopes` |

## Decisions

- **Project key** = workspace `ProjectSlug`, the same project identity Dashboard and Workflow use.
- **System identity** = canonical entity key within the active Target Environment profile scope. No second system list.
- **Approval** = a configuration decision (`SystemConfigurationWrite`). It pins membership only: it is not a test result, not a release decision, and not an execution authorization.
- **Selection** uses approved revisions by default. Drafts are included only when requested explicitly, and a scope with no approved revision produces a notice instead of being silently used. Candidate and excluded members never count.
