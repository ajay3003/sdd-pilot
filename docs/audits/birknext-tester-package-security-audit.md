# Tester package — security audit (local access)

**The "key" is** the local **launch code**:
- 60 random bits, generated by the backend (`LocalSessionService`);
- stored in `…\appdata\local-session\launch-code.txt` with an owner-only ACL (current user + SYSTEM);
- never logged, never in a URL or a static file;
- exchanged once per browser for an HttpOnly, SameSite=Strict session cookie (12 h idle, 7 days absolute);
- sessions live in memory, so a backend restart requires a new exchange;
- the code persists until rotated.

It is not an external API key. No external credential is bundled in the package.

## Automatic connection (new)

1. The launcher, which already reads the owner-only code file, calls `POST /api/local-session/bootstrap` with the code. The backend accepts it only:
   - on a loopback Host (shared guard);
   - with `X-BirkNext-Client: launcher`;
   - **without an Origin header** (every browser POST carries one, so no web page can call it);
   - with the correct code (the same constant-time check and 10-per-minute throttle as manual entry).
2. The backend returns a **one-time token**:
   - 256 random bits;
   - stored only as a hash, in memory;
   - valid **2 minutes**, **single use**;
   - invalidated by code rotation.
3. The launcher opens the browser at `http://localhost:<port>/#bootstrap=<token>`:
   - a **fragment** is never sent to a server and never appears in server logs;
   - the launch code itself is never in a URL.
4. The page removes the fragment from the address bar and the history entry **before** using it, then exchanges it (only from the BirkNext frontend Origin with the client header) for the normal session cookie, and reloads.

**Residual exposure (accepted, documented):**
- The token appears in the browser process's command line for that one launch. Only processes of the same Windows user can read it, and those can read the code file anyway (the design explicitly does not protect against a compromised same-user process).
- The token is useless after its single use or two minutes.
- Manual entry of the code remains the fallback.

**Unchanged:**
- loopback-only binding;
- the CSRF Origin + client-header rule for cookie-authenticated changes;
- Entra bearer handling;
- extension origin confinement;
- every authorization policy.

No authentication was disabled or bypassed. Tests: `LocalSessionBootstrapTests` (code required, single use, expiry, rotation, throttling, browser Origin refused, non-launcher client refused, frontend-only exchange, HttpOnly/Strict cookie, code never echoed), launcher and frontend unit tests.
