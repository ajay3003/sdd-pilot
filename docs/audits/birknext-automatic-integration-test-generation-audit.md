# BirkNext — automatic integration test generation audit

**Audit date:** 2026-11-09  
**Branch:** `008-traceability-first`  
**Method:** static source and existing local artifacts only. No test suite, runtime, database, shared environment, or external service was accessed.  
**Status:** audit complete; Altinn → Skolenærvær evidence case **BLOCKED** pending an explicitly identifiable imported M2LB source snapshot.

## Scope and evidence limits

This report describes code present in the working checkout, not deployed/runtime behavior. The checkout had extensive pre-existing staged/unstaged/untracked work at audit start; it is preserved. The report is the only file added by this audit. The tracked application files were not changed. Test names below establish that tests exist, not that they passed in this audit.

The repository contains `AIAssisted/testdata/M2LB.zip`, related Terraform ZIPs, two Skolenærvær XSD files, local Skolenærvær JSON, and M2LB discovery notes. Those are source/test artifacts, not a registry record proving an imported and analyzed `IqrSourceSnapshot` was selected. This audit did not inspect an application database or infer a selected snapshot from its existence. Consequently the acceptance case does not attribute findings to a particular imported snapshot and is **BLOCKED** as required. Source-level capabilities and the conditional matrix below remain auditable.

## Executive findings

1. BirkNext already has a substantial source-evidence pipeline, canonical contract registry, Test Data catalog, REST/GraphQL draft-test generator, execution/evidence path, topology builder, and a Skolenærvær Integration Journey pack. These are separate capabilities with partial explicit handoffs, not one “generate suite” workflow.
2. REST/GraphQL contracts can produce persisted positive drafts and, on explicit request, negative proposals. The negative proposals remain drafts; expected business outcomes are not guessed. REST/GraphQL calls can execute through the existing controlled execution/evidence engine.
3. XSD, JSON Schema, GraphQL, OpenAPI, AsyncAPI, Terraform, configuration, integration dependencies, Wolverine facts, and message types are discoverable to varying degrees. Discovery does not uniformly create a canonical executable contract or a runnable E2E scenario.
4. Integration Journeys model multi-stage flows and calculate readiness, but the journey runner only executes registered executors/observers. Current registrations cover a bounded Altinn submission/instance observation and message telemetry; the journey model does not thereby make MU, MM, Skoletjenesten, period lock, or Bufdata executable/verifiable.
5. The central manual-work cause is **ownership and identity fragmentation**: the same source snapshot, contract, endpoint binding, environment, Test Data reference, journey integration, and evidence are held by distinct stores and bound through distinct identifiers. Some adapters already bridge them, but there is no operation that takes a selected source snapshot plus integration scope and transactionally assembles/revisions a complete suite.
6. The smallest useful change is an orchestration/draft-generation workflow over the existing engines and stores, with explicit provenance and unresolved-association review. It need not add a new contract, schema, environment, or evidence store, nor a new execution engine.

### Exact distinction between generated and executable

`ContractTestService.GenerateAsync` creates a persisted definition. `ProposeNegativesAsync` creates draft definitions on request and labels those needing assertion configuration. `ContractTestService` readiness/run invokes `ExecutionRunService`; run is a separate explicit action and constrained by environment/auth/safety. `IntegrationJourneyRunner` executes registered steps only. The Journey pack’s scenario descriptor or `spec.md` scenario is not itself a runnable test. Execution Evidence is created only after an actual permitted run/observation. This report did not invoke any such run.

## 8. Smallest target architecture: “Generate Integration Test Suite from Source”

Implement an orchestration service and one workspace over existing services/stores, not another engine:

1. **Select** project and explicit analyzed source snapshot (show fingerprint/date and source repositories).
2. **Discover** Source Analysis facts and call `IntegrationTopologyService`; show candidate systems, edges, contract/schema/config evidence and confidence.
3. **Scope** user chooses integration edges, operations, systems and desired outcomes. Persist the scope as suite definition revision metadata.
4. **Reuse contracts/schemas**: for each approved endpoint/message edge, resolve an existing Contract Registry version or offer an import into that registry from source evidence. Keep XSD/GraphQL/source schema in their existing schema stores and link by identity/version.
5. **Draft environment references** from safe server/config/Terraform evidence. Match to existing Target Environment profiles where confidence permits; never copy secret material or execute a newly guessed URL.
6. **Draft Test Data** using existing catalog providers, schema associations and synthetic policies. Generate only schema-constrained synthetic values with supported rules; unresolved business relationships enter review.
7. **Generate tests** by invoking existing `ContractTestService` for REST/GraphQL positive drafts and explicit negative proposal operation. Include expected assertions only where contract/approved rule establishes them.
8. **Compose E2E** from selected topology edges and Journey pack templates into `IntegrationJourneyDefinition` drafts. Reuse executor/observer coverage; unsupported stages are explicit prerequisites, not omitted.
9. **Link verification** to existing Execution Evidence, message observation, Blob/Parquet observation and journey IDs. Require identity/correlation and expected output contract before marking downstream verification possible.
10. **Calculate readiness** through existing contract and journey readiness services, with a suite-level aggregation of blockers and evidence provenance.
11. **Review uncertain associations** (system alias, route, XSD, field mapping, queue/subscription, environment, identity, output). Approval records must distinguish inferred from confirmed.
12. **Save versioned definitions** in existing contract-test revisions and journey/run-definition ownership, plus references; avoid duplicating contracts, environments, schemas, or evidence.
13. **Execute only on explicit action** through existing authorization/safety checks. Generate itself is draft-only and cannot send requests or messages.

## 10. What blocks real Altinn → Skolenærvær execution

From static repository code, the blocking classes are:

- **Snapshot-specific evidence:** this audit could not establish which explicit imported M2LB snapshot contains which source files; acceptance remains BLOCKED.
- **External-system source and routes:** Altinn-to-MU webhook/subscription, MU outbound routing, MM inbound binding and concrete MM-to-Skoletjenesten API/address require authoritative source/config per environment. A pack profile defines expected candidate edges, not actual deployed routing.
- **Target availability/configuration:** named non-production profiles, application endpoints and any environment-specific queue/entity bindings must be selected and pass existing safety policy. Static Terraform literals are not proof that a target exists.
- **Authentication/authorization:** Altinn actor/app configuration and endpoint credentials/session are separate; no credential value can be extracted from source and should not be generated. Required scopes/tenant/identity need approval.
- **Synthetic identities and relationships:** reporter/child values must be approved for target environment; Person/Tjeneste registration/lookup semantics and test cleanup are prerequisites to meaningful outcomes.
- **MU/MM semantics:** XSD validation, transformation and field mapping require concrete authoritative contracts/rules and an observer. The mere presence of an XSD does not verify the transformed payload or MM behavior.
- **Period lock/corrections/duplicates:** trigger and domain oracle are not safely inferable from a scenario description; correction key, duplicate semantics, state and cleanup need explicit rule/observer.
- **Messaging execution/verification:** source topology and runtime broker metadata are not message send/consume. Each transport action needs an authorized executor and correlation-aware observer. Aggregate telemetry cannot prove a specific submission was handled.
- **Bufdata downstream output:** expected consumer, output object/table format, correlation key and read-only verification contract must be identified. Blob/Parquet inspection alone cannot establish that an output belongs to this submission or is correct.
- **Human approval:** uncertain endpoint/system/field/schema/data mappings and any mutating external execution remain review/authorization gates.

No live status, readiness, authentication or actual availability was assessed in this audit.

## 11. Risks, test strategy and acceptance criteria

### Risks to control

- A source declaration may be mistaken for deployed configuration; preserve evidence class, snapshot and confidence.
- Similar system names or queue names can produce false topology joins; uncertain joins must not become executable without approval.
- Negative API inputs can mutate state despite “negative” labels; keep existing execution safety/confirmation policy.
- Generated test data must remain synthetic, environment-specific, schema-valid and consistent with protected-data rules.
- Aggregate telemetry/checkpoint movement is not per-message proof; do not mark a step verified from these signals alone.
- Cross-store retries can duplicate definitions if generation is not idempotent; use exact source/version/scope identity and existing revisions.
- Draft generation must have no side effects against external targets; only explicit run action can execute.

### Proposed implementation test strategy (not run in this audit)

1. Unit tests for evidence-to-candidate mapping, confidence, source provenance, stable IDs and unsupported-format limitations.
2. Service tests with local/in-memory stores for idempotent generation, exact contract/schema/test-data revisions, scope filtering, stale snapshot and missing prerequisite reporting.
3. Safety tests proving generation performs no network calls, never copies secrets, rejects production profiles and keeps uncertain mappings blocked.
4. Generator tests proving positive/negative REST/GraphQL drafts reuse existing rules, no speculative business assertion is added, XML fixture creation respects schema limits.
5. Journey composition tests verifying order, mandatory steps, existing executor/observer coverage and no pass when downstream evidence is absent or aggregate-only.
6. Local browser tests for provenance display, review/override, blocker navigation and explicit execute confirmation.
7. Local synthetic end-to-end acceptance using fake contracts/targets/observers; do not use shared environments. Real Altinn/M2LB acceptance requires separately authorized non-production setup and is not implied by these local tests.

### Acceptance criteria for the smallest useful release

- Tester can choose an exact analyzed project/source snapshot and view its fingerprint and analyzed contract/topology/config domains.
- Selecting a supported REST/GraphQL topology scope creates saved, idempotent positive drafts and available contract-derived negative proposals through existing services.
- Existing Test Data assets and schemas can be selected/bound from the catalog; any generated fixture is synthetic, versioned and validated.
- Environment, auth requirement, contract, schema, dataset and topology references are prefilled only when evidence is unambiguous; otherwise an explicit review item remains.
- A draft E2E journey has ordered stage definitions, contract test links, expected-verification references and readiness per stage; unsupported transport/domain steps block full readiness.
- Every generated element records source snapshot/fingerprint and evidence source; users can open the owning contract/schema/data/environment/test/journey module.
- Suite generation creates no external calls. Execution uses the existing authorization, safety, authentication and evidence path only after explicit authorization.
- Execution reports distinguish definition generated, request sent, accepted, observed and verified. Missing downstream oracle cannot result in a successful E2E outcome.
- No duplicate contract, environment, schema or evidence store is introduced.

## 12. Direct answers

1. **What can BirkNext already generate automatically?** REST and GraphQL operation-level positive test drafts; bounded contract-derived negative proposals on request; some OpenAPI/Altinn contract bindings and XML fixture/test-data support; and domain pack-authored journey definitions. Actual execution is a separate, explicitly gated action. It does not generally generate a complete integration suite from arbitrary source topology.
2. **Which existing modules are disconnected?** Source Analysis/topology to Contract Registry/Test definitions is partial; schemas to canonical executable contracts is partial; Test Data catalog to generated operation/journey definitions is binding-based; contract calls to Journey steps are not automatically composed; Journey runs to HTTP Execution Evidence and message/blob/parquet observations are not a unified suite evidence graph. There are bridges, but no end-to-end orchestration.
3. **Why does the tester enter information manually?** Separate owners and identities require selecting/binding snapshot, contract version, endpoint/environment, auth reference, dataset/schema, system/route and expected downstream oracle. Some values are not discoverable from static source, secret values are deliberately unavailable, business semantics are not safely inferable, and uncertain topology associations require approval.
4. **What changes eliminate unnecessary manual steps?** Add the draft suite orchestrator/workspace, exact source provenance links and confidence-based prefilling over existing services; auto-call existing contract test and catalog APIs; compose topology-scoped journey drafts and readiness. Review only ambiguous/domain-specific items.
5. **What can be implemented without a new engine?** Phases A–C largely: link source snapshots/topology/contracts, invoke existing REST/GraphQL draft/negative generators, reuse Test Data/schema/environment/readiness services, and save references in existing versioned definitions. API-only integration journeys can be composed using current model/runner where executors exist.
6. **What still requires human review?** System/route alias, producer/consumer and queue association when ambiguous; field mapping/transformation; complex XSD semantics; business validation/period-lock/correction/duplicate oracle; synthetic identity suitability and domain state; environment and auth-reference selection; expected Bufdata artifact and correlation; any external/mutating execution authorization.
7. **What blocks actual Altinn → Skolenærvær execution?** For this audit, the required explicitly identified imported M2LB snapshot is **BLOCKED**. Independently, actual route/config/credentials/non-production target readiness, synthetic identity registration, MM mapping/XSD oracle, messaging executors/observers, period-close trigger, and correlated Bufdata output verifier must be established. Static repository evidence cannot establish runtime availability.
8. **Smallest implementation with useful automatic E2E generation?** A draft-only “Generate Integration Test Suite from Source” orchestration service plus workspace that takes snapshot + approved topology scope, invokes existing Contract Registry/Test Data/REST-GraphQL test generators, composes an existing Journey definition, links readiness/evidence references and presents unresolved prerequisites. Start with supported API calls and mark non-executable message/downstream stages. No new engine or storage infrastructure is needed for this increment.
