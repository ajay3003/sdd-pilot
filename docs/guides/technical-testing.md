# Technical testing in BirkNext — a guide for testers

Technical testing covers what a person does not check by hand: load and performance, automated browser flows and integration chains. This
guide follows what was run end to end on an isolated BirkNext (Release build, empty database) against local stand-in systems. Nothing in these
runs contacted M2LB, MU, MM, Altinn, TT02 or any other real environment. Where a step needs a real, attended environment, the guide says so and
gives a checklist.

| Area | Page | Needs |
|------|------|-------|
| Performance and load | Performance Test Review (`/performance-test-review`) | A non-production target reachable from the k6 container (Podman) |
| Automated browser flows | Critical E2E Regression (`/critical-e2e-regression`) | An imported project with UI source; for verify and run, the Edge Companion on an attended page of a non-production target |
| API quality | API Quality Review (`/api-quality-review`) | A non-production Target Environment with the API's base URL (and health endpoint, OpenAPI contract) |
| Front-end quality | Frontend Quality Review (`/frontend-quality-review`) | A non-production Target Environment with the front end's URL; Chromium, Node (Lighthouse) and Podman with the ZAP image on the BirkNext server for the browser engines |
| Integration chains (Skolenærvær) | Integration suites (`/integration-suites`) | A project, the services' source (OpenAPI) and a non-production Target Environment whose URL reaches every stage |

Manual test cases are prepared in **Manual Testing → Plan & prepare** and exported to Azure DevOps Test Plans
([manual-testing-m2lb.md](manual-testing-m2lb.md)); the technical pages do not prepare manual test cases.

## 1. Performance Test Review

Performance Test Review puts controlled HTTP load on a target, measures latency, throughput and errors, compares a run with an approved
baseline and exports a report. The load is generated by **k6** (`docker.io/grafana/k6:1.0.0`) in a short-lived **Podman** container.

### Before you start

- **A Target Environment** (System Settings → Target Environments) of type Local, Development, QA, Test or RC, with the target's URL.
  Production — and any environment whose type is unknown — is refused. Only the scheme, host and port of the URL are used; the scenario's
  paths are relative to it.
- **Podman running** with the k6 image. The page's *Execution runtime*, *Provider image* and *Provider* readiness items say whether they are.
- **The target must be reachable from the k6 container**, not only from your machine. A service that listens only on `127.0.0.1` of your
  PC is *not* reachable from the container; a container port published on all interfaces is. A VPN or corporate DNS that exists only on
  your PC may also be missing in the container. The readiness check tests this before any load.
- Only read-only requests (GET, HEAD, OPTIONS) with relative paths; no credentials in headers.

### Step by step

1. **Open Performance Test Review.** The header shows the Target Environment in use. Choose **New** for a new test definition.
2. **Scenario tab.** Give the test and the scenario a name. Choose **Add manual step** and enter the path (for example `/api/items`), the
   expected status and the think time between requests (500 ms by default — lower it to get more samples from a short run).
3. **Workload tab.** Virtual users and the phases (warm-up, ramp-up, steady state, ramp-down). The smallest allowed run is 1 virtual user
   with 10 s steady state; a short check such as 2 users × 12 s takes about 20 s including the container start.
4. **Thresholds tab.** Two required thresholds are there from the start: P95 < 500 ms and error rate < 1 %. Choose **Add drift policy**
   (P95, +20 % accepted by default). **Without a drift policy, a later run is compared with the baseline but never assessed as a
   regression** (*Comparison only*). Add it before the first run.
5. **Save.** The first save creates version 1. Changing a saved definition needs *Save changes as new version*; Run is disabled while
   changes are unsaved.
6. **Readiness tab → Check readiness.** Every item must be *Ready* or *Optional*. *Target reachability* is one GET from a k6 container to the
   target; it stays valid for 15 minutes and is repeated just before every run (an unreachable target makes the run *Blocked*, with no load).
7. **Run tab → Start run.** Progress is shown while k6 runs. **Results** then shows the outcome:
   - *Run completed · Thresholds passed* (or failed), the requests, failed requests, throughput and P50 · P90 · P95 · P99 latency;
   - *Baseline snapshot* — each metric against the baseline, with the change and the assessment.
8. **Make a run the baseline.** History → **Propose as baseline** on a completed run. The eligibility list must be green (completed, complete
   metrics, at least 20 requests for P95, no dropped iterations, required thresholds met); accept any warning explicitly, give a reason and
   choose **Propose and approve now** (or **Propose**, and approve later with **Approve**). A run never becomes the baseline by itself.
9. **Run again** after the change you want to measure. Results now shows the baseline verdict next to the threshold outcome, for example
   *Thresholds passed · Regression against baseline v1*: thresholds and the baseline are separate questions, and a run can pass its
   thresholds while it regressed against the baseline.
10. **Compare tab.** The regression comparison of the latest run with the baseline, metric by metric. One run after the baseline gives at most
    *Potential regression*; three runs confirm it (*Confirmed regression*). Metrics need enough samples (P95: 20 requests, P99: 100) or they
    are *Inconclusive*. Throughput and error rate are assessed only when they have a drift policy of their own.
11. **Report.** Results → **Export HTML** downloads `performance-test-<run>.html`: the run, workload, all metrics, thresholds, the baseline
    comparison with its verdict, limitations and provenance (engine, image digest, definition version). Compare → **Export** gives the
    regression comparison as JSON.

### Reading the results

| You see | It means |
|---------|----------|
| *Thresholds passed* | The configured expectations held for this run (absolute limits) |
| *Regression against baseline v1* | A metric with a drift policy is worse than the baseline by more than the accepted change |
| *Degraded within tolerance* | Worse than the baseline, but within the accepted change |
| *Potential* / *Confirmed regression* | One run / three runs after the baseline show the regression |
| *Inconclusive* | Too few requests for that percentile |
| *Comparison only (no drift policy)* | The run is compared with the baseline, but nothing is assessed — add a drift policy |
| *Blocked* | The target was not reachable from the k6 container just before the run; no load was sent |

Load-test latency is the latency under this workload from this load generator. It is not the latency of a single request (API Quality
Review) or browser performance (Frontend Quality Review).

### Troubleshooting

| Problem | Do this |
|---------|---------|
| *Target reachability* fails | Make the target reachable from a container: publish its port on all interfaces, or use the target's real DNS name; check proxy and CA settings (System Settings → Performance Test Engines) |
| Start run is disabled | Save the definition, check readiness (valid 15 minutes), wait for an active run to finish; production targets are never run |
| No regression verdict | Add a drift policy on Thresholds (before the run) and make sure a baseline is active |
| The baseline proposal shows warnings | Fewer than 20 requests for P95, dropped iterations or failed thresholds: run longer or with more users, or accept the warning with a reason |

### What was verified

`PerformanceTestReviewWorkflowTests` (browser test, real k6 in Podman) against a local stand-in target
(`frontend/BirkNext.Web.PlaywrightTests/performance-target`, a small server whose response time the test sets):

- Scenario `/api/items`, 2 virtual users × 12 s, P95 drift policy; saved v1; readiness all *Ready*.
- Run 1 at about 20 ms: 83 requests, P95 22.2 ms, thresholds passed → proposed and approved as baseline v1.
- The target was made ten times slower → run 2: P95 252.7 ms (+1040 %), throughput −76 %, thresholds still passed; Results shows
  *Regression against baseline v1*, Compare shows P95 *Potential regression*, and the HTML report carries the same comparison and verdict.
- Also verified on a database with an existing definition and baseline (a tester's return visit).

To run it yourself: start the stand-in with `performance-target/start-target.ps1`, start an isolated BirkNext, set
`BIRKNEXT_PLAYWRIGHT_FRONTEND_URL`, `BIRKNEXT_PLAYWRIGHT_BACKEND_URL`, `BIRKNEXT_PLAYWRIGHT_LAUNCH_CODE_FILE` and
`BIRKNEXT_PERFORMANCE_TARGET_URL`, and run `dotnet test BirkNext.Web.PlaywrightTests --filter FullyQualifiedName~PerformanceTestReviewWorkflowTests`.

**Against a real environment (attended):** create a Target Environment for the DEV/QA/TEST service, check *Target reachability* first,
start small (1–2 users, 10–30 s), agree the load with whoever owns the service, and promote a baseline only from a run you trust.

## 2. Critical E2E Regression — suggested browser tests

Critical E2E Regression turns the UI found in the imported source (pages, links, search, forms, buttons) into **suggested** browser tests,
checks their element locators on the real page with the **Edge Companion**, and runs approved tests as automated flows in your own signed-in
Edge. The steps run automatically; *attended* means you sign in yourself and keep the page open while they run.

Manual test cases are not prepared here: use Manual Testing → Plan & prepare (the same UI scenarios are discovered there) and Azure DevOps.

### What needs what

| Step | Needs |
|------|-------|
| Generate and review suggestions | An imported project with UI source and a Target Environment (any non-production type). No browser, no Companion |
| Verify locators, approve, run | The Edge Companion paired with BirkNext and **exactly one** approved page of the target open in Edge, on the suggestion's route |
| Run | A Development, QA, Test, RC or Local Target Environment (production — or an unknown type — is refused) |

### Step by step

1. **Open Critical E2E Regression.** The *Attended browser* card says whether the Companion is connected and which approved page is open.
2. **Suggested tests → Source snapshot →** choose the imported project's snapshot → **Generate suggestions.** Nothing runs. The summary counts
   the suggestions (for M2LB: 59 from 61 UI files — 48 UI functional, 11 page checks) and what they still need (DOM mapping, expected
   result, Test Data).
3. **Review a suggestion.** It shows the steps in words, the expected result (only when the source states one; otherwise *NEEDS EXPECTED
   RESULT*), the source file and line, and preconditions. Under the buttons:
   - *To verify locators:* what is missing for **Verify DOM in Edge** (pair the Companion, open the page, go to the route);
   - *To approve:* the list of what still stops approval — a step without an accepted locator, Test Data to choose, no expected result, an
     existing flow that already covers it. The buttons stay disabled until the list is empty, so nothing is refused after the click.
4. **Verify DOM in Edge.** The Companion checks each locator on the open page (*Verified unique*, or why not). **Accept** the locator per
   step (or choose an alternative). Choose approved Test Data for each placeholder, and state the expected route when the source states none.
5. **Approve test.** The suggestion becomes a **Diagnostic** flow, shown at once in the flow list with its **Run** button. Diagnostic
   flows never count as release evidence; a flow becomes release-critical only when you make it one in the flow editor.
6. **Run.** The Companion performs the steps on the attended page. The run says *Diagnostic pass*, *Failed* (with what was expected and
   what was observed, for example *Expected route /children/new, observed /children/old-form*) or *Blocked* (the page or the Companion
   was not available — not a test result).

### Pairing the Edge Companion

Install the Companion in Edge, open **Browser Companion** in BirkNext (or *Prepare attended browser* on Critical E2E), generate a pairing
code for the Target Environment and enter it in the Companion's popup. The pairing approves only that environment's origin; the Companion
never reads cookies, storage or headers.

### What was verified

`CriticalE2ECompanionWorkflowTests` (browser test) with the **real** Companion extension paired with an isolated BirkNext, against a
stand-in single-page application that the browser serves itself (no network): import a project with Razor UI → pair → *Attended browser:
Ready* → generate → *To approve: … no accepted locator* → Verify DOM in Edge → *Verified unique* → accept → approve → the flow is shown →
run → *Diagnostic pass* (4 of 4 steps) → the stand-in's link changed → run → *Failed: Expected route /children/new, observed
/children/old-form*. On real M2LB data (offline part): 59 suggestions generated in about 2 s, reviewable, no page errors.

**Against the real application (attended):** pair the Companion with the DEV/QA Target Environment, sign in to the application in Edge
yourself, open the suggestion's page, verify, approve and run one flow at a time. A full page reload during a step (instead of an in-app
route change) ends that step as *Blocked*: keep one page of the application open and let the flow navigate inside it.

## 3. The Skolenærvær chain — Altinn → MU → MM → Skole → Bufdata

Integration suites tests the whole chain as one composite run: a report is submitted in Altinn, received by MU (Meldingsutveksleren), validated
by MM, ingested by SkoleService, the person is looked up, the period is locked and the delivery reaches Bufdata. BirkNext makes the
data-changing calls (submit, period lock) once each and *observes* the other stages, following the identifiers each stage returns (submission
→ message → report → period) across every boundary.

The Skolenærvær page (`/extensions/skolenaervaer`) shows readiness per journey; the composite run itself is started in **Integration suites**.

### Before you start

- **A project** in BirkNext (Import Project). A suite belongs to one project; without one, Generate says so.
- **The services' source** with their OpenAPI contracts, as Source Analysis snapshots (Import Project, or Source Analysis → upload). The
  stages are recognised from the folder and project names (Altinn app, Meldingsutveksler, Meldingsutveksler receiver, SkoleService, Person,
  Bufdata delivery).
- **A Target Environment** of type Local, Development, QA or Test whose URL reaches every stage (production is refused). The chain is called
  on that one origin; a stage's base path comes from its contract binding.

### Step by step

1. **Integration suites → Sources.** Choose the scope *Altinn → MU → MM → Skolenærvær → Bufdata* and **Discover**. BirkNext proposes one
   source per stage (for example *package A: altinn, mu*). **Approve** each proposal and **Save** — the composite context gets a revision.
2. **Generate.** *Generate draft suite* writes a draft; nothing is sent. Readiness lists what still needs a person (for example a Kode 6/7
   domain decision).
3. **Execute.** The plan lists the stages in order (altinn → mu → mm → skole-intake → person-tjeneste → period-lock → bufdata) with their role:
   the first stage *executes*, later stages are *observed*, the period lock is an *action*. **Approve the plan.**
4. **Preflight** says whether this is a full end-to-end run (*FULL_E2E*) or a subflow and names the data-changing calls. Tick **Confirm
   data-changing calls** and **Authorise this run** (authorisation is for one run only) and **Run**.
5. **The run follows itself** until it ends: each stage's state, each boundary's correlation (*altinn → mu: Confirmed*) and the verdict.

### Reading the verdict

| Verdict | Meaning |
|---------|---------|
| *FULL_E2E_VERIFIED* | Every stage was observed and every boundary's correlation was confirmed |
| *SUBFLOW_VERIFIED* | The chosen part of the chain was verified — never reported as full end to end |
| *INCOMPLETE* | A stage was not observed within its bounded waiting (*TimedOut*) — a rejected or lost message looks like this; it is not a pass and not proof of a failure |
| *WRONG_CORRELATION* | A stage answered with another message's identifier |
| *FAILED* / *UNKNOWN_OUTCOME* | A call failed, or a data-changing call got no answer (never retried automatically) |

### What was verified

`SkolenaervaerChainWorkflowTests` (browser test) against a local stand-in of every system (`SkolenaervaerStandIn`, with its own ledger):
project → four source packages → discover, approve, save → generate → approve plan → preflight *FullE2E* → run: **FullE2EVerified**, 7 stages
succeeded, 6 correlations confirmed, the stand-in's ledger shows one report through all seven transitions and exactly two data-changing calls;
MM rejecting → **Incomplete** (MM *TimedOut*); MM answering with another id → **WrongCorrelation**.

**Against TT02 / MU / MM (attended):** create a Target Environment for the test environment, bind each contract's base path, run a
**subflow** first (for example Altinn → MU) before the full chain, and agree the submission with whoever owns the receiving systems.

## 4. API Quality Review

API Quality Review calls the API's read-only operations once, checks the answers against its OpenAPI contract, reviews the contract
document itself, and checks security headers, CORS, error handling and response times. It never sends data-changing requests in the main
run (safe fuzzing and authorization checks are separate, opt-in checks).

### Before you start

A Target Environment (Local, Development, QA or Test) with the API's **REST base URL**, optionally a **health endpoint** and the **OpenAPI
contract URL** (System Settings → Target Environments). The run calls those URLs and any operations Endpoint Discovery has observed; it does
not call every operation listed in the contract.

### Step by step

1. **Open API Quality Review.** The run decision says *Ready*, *Limited* or *Blocked* and why; the target cards show what will be called and
   which contract is used.
2. **Run review.** One run takes a few seconds per target.
3. **Overview** shows the key issues (grouped by rule and endpoint) and the severity strip; **Findings** lists every finding with its
   evidence; **Contracts** shows the contract checks and drift; **Security**, **Errors** and **Performance** show their checks.
4. **Run review again** after a change. The second run also reports *drift* — what changed in the live responses since the previous run.
5. **Export → HTML** downloads `api-quality-review-<date>.html`.

### What the findings mean (examples)

| Finding | Meaning |
|---------|---------|
| *Unexpected type at $[*].id*, *Missing required property $[*].name* (High, Breaking) | A live response does not match the contract — for an array, every element is checked against the item schema |
| *No security schemes declared* (Medium) | The contract does not say how clients authenticate |
| *Server error HTTP 500* (High) | A read-only call failed on the server |
| *Wildcard CORS origin combined with credentials* (High) | Any web site may call the API with the user's cookies |
| *Unknown route causes HTTP 500* / *Error response leaks internal details* (High) | Errors are not handled; stack traces or file paths are returned |
| *API served over plain HTTP* (High) | Expected on a local stand-in; never acceptable in a real environment |
| *Slow response* (Low) | A single request was slower than the latency policy (1500 ms by default) |

### What was verified

`ApiQualityReviewWorkflowTests` (browser test) against a local stand-in API (`ApiStandIn`) with deliberate defects: the run reports the
server error, both contract violations, unsafe CORS, the leaking error page, the slow response, the missing headers and the contract's
missing security scheme; after the stand-in is fixed, those findings are gone, plain HTTP and the unchanged contract are still reported,
and the HTML report is downloaded. Two defects in BirkNext were found and fixed on the way: an array of component items was not checked
element by element (a wrong type and a missing required property read as "1 undocumented property", Info), and the contract document's
own findings never reached the review's findings.

## 5. Frontend Quality Review

Frontend Quality Review reviews a web front end with up to six automated engines and turns their findings into one list of logical issues
and a release decision:

| Engine | What it checks | Runs where |
|--------|----------------|------------|
| HTTP Security | Expected security headers (CSP, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, HSTS on HTTPS), CORS, exposed configuration and source maps, cookies | BirkNext backend (HTTP) |
| HTTP Performance | Caching headers, compression and size of the page's CSS/JS/fonts/images | BirkNext backend (HTTP) |
| Browser Runtime | Script errors, console errors and failed requests while the page loads | Chromium in the BirkNext backend |
| Accessibility | axe-core WCAG 2.x A/AA rules on the rendered page | Chromium in the BirkNext backend |
| Lighthouse | Performance audits (cache policy, render-blocking resources, unused code, …) | Node + Chromium in the BirkNext backend |
| Passive Web Security | OWASP ZAP passive rules on one page load (no attack, no spider) | ZAP container (Podman) |

Severity alone never blocks a release. A result is **Blocked** only when a required engine could not assess the target or an issue is listed
in the Target Environment's release policy. When Accessibility ran, the best result is **Review required**, because automated checks never
replace manual WCAG testing.

### Before you start

- A Target Environment (Local, Development, QA or Test) with the front end's URL. Turn on the engines you want under **Engines**.
  Optionally, list release-blocking issues in its release policy (for example `headers:csp:missing`).
- The installation has to allow the browser engines. Browser Runtime, Accessibility, Lighthouse and Passive Web Security are switched on
  per installation (`FrontendQualityCapabilities`, `FrontendQualityEnginePreferences`). Lighthouse needs Node and its runner packages
  (`npm ci` in `Tools/LighthouseRunner`). Passive Web Security needs Podman, the pinned ZAP image, and the Target Environment registered for
  passive scanning on the server (`FrontendPassiveSecurity:TrustedProfiles:<environment id>`).

### Step by step

1. **Open Frontend Quality Review.** Each engine card says *Enabled* or *Ready*, or why it cannot run. While the runtime check is still
   running, a card says so: it does not say "not available".
2. **Run Frontend Quality Review.** A run takes about a minute with all six engines.
3. **Summary** shows the release decision and the key issues. **Issues** lists every logical issue. One issue can come from several
   engines: a missing CSP is reported by HTTP Security, the standards check and ZAP, and appears once. **Coverage** shows each engine's
   outcome (*View engine diagnostics* opens the engine matrix). **Evidence** shows the details. **History** keeps your last ten runs in
   this browser.
4. **Run again** after a fix. The new result replaces the old one, and both runs stay in **History**.
5. **Export → HTML** downloads `frontend-quality-review-<date>.html`.

### What the issues mean (examples)

| Issue | Meaning |
|-------|---------|
| *Content Security Policy header missing* (Critical) | The page can run any script; a team rule can make it release-blocking |
| *TypeError: cannot read properties of undefined* (Browser Runtime, High) | A script failed while the page loaded |
| *Failed important resource* (High) | A script or stylesheet the page needs answered 404/500 |
| *Images must have alternative text*, *Form elements must have labels*, *Buttons must have discernible text* (Accessibility, Critical) | axe-core WCAG violations; the element selectors are under the issue |
| *Contrast (minimum)* (WCAG 1.4.3) | Text is too faint for its background |
| *Static assets missing caching headers* (HTTP Performance), *Serve static assets with an efficient cache policy* (Lighthouse) | Every visit downloads CSS/JS again |
| *Cookie no HttpOnly flag*, *Cookie without SameSite attribute* (ZAP, Low) | A session cookie is readable by scripts / sent cross-site |

### What was verified

`FrontendQualityReviewWorkflowTests` (browser test) against a local stand-in website (`frontend-target/server.js` in Podman) with all six
engines on.

- **Broken site:** every engine completed and found what it is for. The release was **Blocked** by the team rule on the missing CSP.
- **Fixed site:** all of those issues were gone, the decision was **Review required** with full coverage, both runs were in History, and
  the HTML report named the site.

Seven defects in BirkNext were found and fixed on the way:

1. Accessibility could not review a site with a strict Content-Security-Policy: the injected axe script was refused.
2. Accessibility failed on pages with several defects (*"requires an element of type 'Array'"*).
3. ZAP's own "ZAP is out of date" notice was reported as an issue of the tested site.
4. Before the runtime check had run, four engines were shown as "not available in this environment".
5. A clean accessibility run and a site with all expected headers read as "No evidence", so a clean site could never get full coverage.
6. A published installation had no Lighthouse runner packages, so Lighthouse could never run there. The workflow-test script now copies
   them; a real installation needs `npm ci` in `Tools/LighthouseRunner`.
7. On a busy machine, Lighthouse and Accessibility were skipped as "Not ready". The run gave every engine's readiness check 5 s, while
   Lighthouse's own check may take 35 s and a Chromium start more than 5 s. The run now waits for each engine's own budget.

## 6. All workflow tests in one command (before a release)

`scripts/run-workflow-tests.ps1` runs every browser workflow test in this guide (and the Manual Testing ones) on a throw-away installation:

```powershell
# from the repository root; Podman's PostgreSQL (birknext-studio-local_postgres_1) must be running
.\scripts\run-workflow-tests.ps1                                  # all workflow tests except the three below
.\scripts\run-workflow-tests.ps1 -M2lbArchive "$env:USERPROFILE\Downloads\M2LB (8).zip" -Performance -FrontendQuality   # the full set
.\scripts\run-workflow-tests.ps1 -Filter "FullyQualifiedName~ApiQualityReviewWorkflowTests" -NoPublish  # one test, reuse the last publish
```

What it does:

1. Copies the source (without `bin`/`obj`) into `%TEMP%\birknext-workflow-tests` and publishes the API and the web app in Release from that
   copy, then checks the web app's integrity hashes (a stale `dotnet.native.wasm` would otherwise stop the browser from loading the app).
2. Creates a fresh database `birknext_wf_<time>`; the API migrates it on start.
3. Starts the API (a local tester installation: Production, loopback only) and the web app on their own free ports. Your own BirkNext on
   5000/5173 and its database are not touched.
4. Runs the real-data M2LB test first, on the empty database (with `-M2lbArchive`), then all other workflow tests; `-Performance` also starts
   the k6 stand-in target and `-FrontendQuality` the stand-in website (both in Podman). The API gets its own settings: every Frontend
   Quality Review engine allowed and only the stand-in registered for ZAP; your `appsettings.Local.json` is never copied.
5. Stops everything it started, drops the database (`-KeepDatabase` keeps it) and prints a result table. Exit code 0 = everything passed.

Logs and the test result files are in `%TEMP%\birknext-workflow-tests\logs`. Nothing external is contacted. A green run is the last local step
before a release; the release itself (push, pipeline, deploy) is a separate, deliberate step.
