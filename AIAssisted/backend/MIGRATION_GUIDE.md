# EF Core Migration Guide

## Overview

Database schema changes in BirkNext use Entity Framework Core Code-First Migrations. This guide explains how to create, apply, and maintain migrations safely.

## Quick Start

### Creating a New Migration

1. **Make changes to your DbContext model** in `BirkNext.Api/Data/AppDbContext.cs`:
   ```csharp
   public DbSet<MyNewEntity> MyNewEntities => Set<MyNewEntity>();
   ```

2. **Add a new migration**:
   ```bash
   cd BirkNext.Api
   dotnet ef migrations add AddMyNewEntity
   ```

3. **Verify the migration**:
   ```bash
   dotnet ef migrations list
   ```
   Output should show your new migration without "Pending" status.

4. **Apply the migration**:
   ```bash
   dotnet ef database update
   ```

### Checking Migration Integrity

Before committing, verify migration integrity:

```bash
# Run the check-migrations script
./check-migrations.ps1

# Or run tests
dotnet test --filter MigrationIntegrity
```

## Migration Files Structure

Each migration consists of **two required files**:

### 1. Migration .cs File
Contains the `Up()` and `Down()` methods:

```
20260702120000_AddWorkspaceReviewSteps.cs
```

```csharp
public partial class AddWorkspaceReviewSteps : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        // SQL to apply this change
        migrationBuilder.CreateTable(...)
    }

    protected override void Down(MigrationBuilder migrationBuilder)
    {
        // SQL to revert this change
        migrationBuilder.DropTable(...)
    }
}
```

### 2. Designer .cs File (Generated)
Contains metadata about the migration:

```
20260702120000_AddWorkspaceReviewSteps.Designer.cs
```

**Important**: This file is generated automatically by `dotnet ef migrations add`. Do NOT create it manually.

### 3. Model Snapshot (Shared)
```
AppDbContextModelSnapshot.cs
```

This is updated automatically to reflect the current model state after each migration. It shows what the DbContext looks like after all applied migrations.

## Common Scenarios

### Scenario 1: Add a New Table

```bash
# 1. Add the entity to AppDbContext
# In AppDbContext.cs:
# public DbSet<Customer> Customers => Set<Customer>();

# 2. Create migration
dotnet ef migrations add AddCustomersTable

# 3. Apply migration
dotnet ef database update
```

### Scenario 2: Add a Column to Existing Table

```bash
# 1. Add property to the entity class
# In Models/Customer.cs:
# public string PhoneNumber { get; set; }

# 2. Create migration
dotnet ef migrations add AddPhoneNumberToCustomer

# 3. Apply migration
dotnet ef database update
```

### Scenario 3: Remove a Column

```bash
# 1. Remove property from entity
# In Models/Customer.cs:
# public string Email { get; set; }  // Remove this line

# 2. Create migration
dotnet ef migrations add RemoveEmailFromCustomer

# 3. Apply migration
dotnet ef database update
```

### Scenario 4: Rename a Column

```bash
# 1. Rename property in entity
# From: public string Name { get; set; }
# To:   public string FullName { get; set; }

# 2. Create migration
dotnet ef migrations add RenameNameToFullName

# Then EDIT the migration to use RenameColumn instead of Drop/Create:
# migrationBuilder.RenameColumn("name", "customers", "full_name");

# 3. Apply migration
dotnet ef database update
```

## Do NOT Do This

### ❌ Never Hand-Create Migration Files

**WRONG:**
```
Manually create:
20260702120000_AddCustomers.cs
20260702120000_AddCustomers.Designer.cs
```

**CORRECT:**
```bash
dotnet ef migrations add AddCustomers
```

### ❌ Never Create Designer Files Manually

The `.Designer.cs` file must be generated by EF Core tooling. It contains model metadata that EF Core produces automatically.

### ❌ Never Edit Designer Files

Designer files are generated code. If you edit them, EF Core will regenerate them anyway on the next command, overwriting your changes.

### ❌ Never Skip Designer Files

If you see a migration without a `.Designer.cs` file, it's incomplete and will NOT be applied by EF Core.

## Troubleshooting

### Untracked Migrations

**Symptom:**
```
$ dotnet ef migrations list
20260507124300_InitialCreate
20260527100158_AddReviewedCandidates
(missing: 20260702120000_AddWorkspaceReviewSteps)
```

**Cause**: Migration .cs file exists but `.Designer.cs` is missing.

**Fix**:
1. Check that `.Designer.cs` file exists for your migration
2. If missing, delete the `.cs` file and run: `dotnet ef migrations add <Name>`
3. Run: `dotnet ef database update`

### Pending Migrations

**Symptom:**
```
$ dotnet ef migrations list
20260702120000_AddWorkspaceReviewSteps (Pending)
```

**Cause**: Migration exists but hasn't been applied to database.

**Fix**:
```bash
dotnet ef database update
```

### Designer File Orphaned

**Symptom:** Designer file exists but no corresponding migration .cs file

**Cause**: Migration was deleted without removing Designer file

**Fix**: Delete the orphaned `.Designer.cs` file

### Diverged Model/Snapshot

**Symptom**:
```
$ dotnet ef migrations add FixModel
warning: The model snapshot 'AppDbContextModelSnapshot' has changed but
no migrations have been added for the changes in 'AppDbContext'.
```

**Fix**:
1. Run: `dotnet ef migrations add <DescriptiveName>`
2. Review the generated migration
3. Run: `dotnet ef database update`

## Migration Integrity Checks

The system automatically validates:

1. **File Completeness**: Every .cs has matching .Designer.cs
2. **Designer Presence**: No orphaned Designer files
3. **EF Recognition**: All migrations tracked by EF Core
4. **Snapshot Currency**: Model snapshot is up to date
5. **Migration Attributes**: All migrations have [Migration("...")] attribute

### Running Checks

**PowerShell Script:**
```bash
./check-migrations.ps1
```

**Unit Tests:**
```bash
dotnet test --filter MigrationIntegrity
```

**Environment Diagnostics:**
Open System Settings → Developer → Environment Diagnostics, scroll to "EF Migration Integrity"

## CI/CD Integration

The build pipeline runs migration integrity checks before tests:

1. `check-migrations.ps1` runs as pre-test validation
2. `MigrationIntegrityTests` xUnit tests run during test phase
3. Build fails if any critical issues found

This prevents migrations with missing Designer files from being merged.

## Best Practices

### 1. Always Use `dotnet ef migrations add`

```bash
# ✓ Good
dotnet ef migrations add AddUserEmail

# ✗ Bad - creates incomplete migration
copy SomeMigration.cs NewMigration.cs
```

### 2. Descriptive Migration Names

```bash
# ✓ Good - clear what changed
dotnet ef migrations add AddUserEmailColumn
dotnet ef migrations add RemoveDeprecatedField
dotnet ef migrations add RenameTableToPlural

# ✗ Bad - ambiguous
dotnet ef migrations add Update
dotnet ef migrations add Fix
```

### 3. Review Generated Migrations

Before applying:

```bash
# Review the SQL that will be generated
dotnet ef migrations script <FromMigration> <ToMigration>

# Check the generated migration file
cat Data/Migrations/20260702120000_AddField.cs
```

### 4. Test Before Committing

```bash
# 1. Create migration
dotnet ef migrations add MyChange

# 2. Apply locally
dotnet ef database update

# 3. Run tests
dotnet test

# 4. Verify migrations script
dotnet ef migrations list  # Should show no "Pending"

# 5. Commit
git add .
git commit -m "Add migration: MyChange"
```

### 5. Handle Conflicts Carefully

If migrations conflict during merge:

```bash
# Don't manually edit timestamps - rebase
git rebase --continue

# OR remove conflicted migration and re-add
git rm Data/Migrations/20260702*
dotnet ef migrations add <ReNamedForNewTimestamp>
dotnet ef database update
```
